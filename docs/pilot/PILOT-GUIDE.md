# Harness 小白可用性试点指南（HTH-020）

> 目标画像：能使用 AI Coding，但不了解 Gate / Evidence / CI 的开发者。
> 本轮为可执行试点包；实际招募与执行需外部协调（≥10 人完成）。

## 1. 招募（10–15 人）

| 条件 | 说明 |
|---|---|
| 会用 AI Coding（Copilot / Codex / Cursor 等） | 熟悉"让 AI 改代码"的工作方式 |
| 不了解 Gate / Evidence / CI 概念 | 不能是 Harness 或类似系统已有用户 |
| 有可写代码的项目 | 个人项目即可，无需生产环境 |
| 时间 | 每人约 1.5–2 小时（3 个任务 + 访谈） |

> 不招募：本仓作者、看过本方案的人、CI/CD 平台工程师。

## 2. 环境准备

- 提供干净目录（git init 完成、任意语言的 hello-world 项目）
- 安装 `npx harness setup --preset single --tier lite`（或按预设指定）
- 记录试点前状态：`harness doctor` 输出截图

## 3. 三个任务

### 任务 1：安装 + 首个低风险修改（≤30 min）

1. 安装 Harness 并完成 setup
2. 用一句话需求（带前缀，如 `优化：xxx`）让 AI 完成一次低风险修改（如改一个文案）
3. 目标：走完 task → gate → 修改 → 提交 的完整首环

**记录**：完成率、首次可信提交时间、显式命令数、复制 ID 次数、求助次数。

### 任务 2：验证后修改（≤30 min）

1. 在上一步已完成验证的任务上，**再次修改同一文件**（制造验证后变更）
2. 观察系统是否正确阻断（evidence stale / verify-test 失效）并帮助恢复
3. 目标：理解"证据绑定变更"的含义

**记录**：是否被正确阻断、是否自行恢复、误阻断、绕过尝试。

### 任务 3：标准风险任务 + 文档同步（≤30 min）

1. 完成一个需要文档同步的标准风险任务（如新增 API 端点）
2. 观察 doc-impact / sync-check 提示
3. 目标：理解"代码改了，文档必须同步"

**记录**：完成率、显式命令数、求助次数、误阻断。

## 4. 执行流程

1. 试点前：发放指标表，说明 3 个任务，不解释 Gate/Evidence 概念
2. 试点中：观察者记录（不主动提示，除非任务卡死 > 10 min）
3. 试点后：立即访谈（30 min，见 `interview-guide.md`）
4. 数据回收：`harness metrics export`（用户先审阅再决定是否提供）
5. 整理：填 `issues-report-template.md`，按严重度分级

## 5. 指标定义（对齐 §7.2）

| 指标 | 定义 |
|---|---|
| 完成率 | 3 个任务全部完成的人数 / 总人数 |
| 首次可信提交时间 | 任务 1 从开始到首个提交通过验证的分钟数（P50/P90） |
| 显式命令数 | 用户手动输入的非向导命令条数 |
| 复制 ID 次数 | 复制/粘贴 Task/Gate/check ID 的次数 |
| 求助次数 | 向观察者提问的次数 |
| 误阻断 | 系统阻止了本应成功的操作（记录详情） |
| 绕过尝试 | 用户尝试跳过/禁用 gate 的次数 |
| 可信理解 | 访谈中能否复述当前保护层与剩余风险 |

## 6. 问题分级

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 数据丢失 / 破坏 / 无法完成任何任务 | 立即修复，暂停试点 |
| P1 | 任务失败率高或严重误导 | 本批次内修复 |
| P2 | 可用性摩擦（复制 ID、命令多） | 排期优化 |
| P3 | 建议/打磨 | 记录 backlog |

## 7. 试点结论输出

- 汇总完成率、P50/P90 首可信提交时间、误阻断率、显式人工动作数
- 对照 §7.4 发布条件（≥80% 完成率、P50≤10min、误阻断<5%、人工动作 P50≤3）
- 输出前 10 个摩擦点 + 修复建议
- 写入 `docs/rfc/0003-release-gate.md` 的证据区
